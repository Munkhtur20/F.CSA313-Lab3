## 3. Системийн API

| Endpoint | Method | Үйлдэл |
|---|---|---|
| /cart/add | POST | Сагсанд бараа нэмэх |
| /report | GET | Тайлангийн мэдээлэл буцаах |

API сервер localhost:3000 дээр ажиллана.

- `/pay` – 5%-ийн магадлалаар HTTP 500 алдаа буцаана.

## 5. SLI ба SLO

SLI нь системийн чанарыг хэмжих үзүүлэлт. SLO нь тухайн үзүүлэлтэд тавьсан зорилтот босго юм.

| Чанар | SLI | SLO | Хэмжих нөхцөл |
|---|---|---|---|
| Performance | Cart response p95 | < 50 ms | 20 VU, 1 минут |
| Reliability | Pay HTTP failure rate | < 8% | 20 VU, 1 минут |
| Availability | Cart successful request rate | > 90% | 20 VU, 2 минут, серверийн тасалдал |
| Performance | Report response p95 | < 450 ms | 20 VU, 1 минут |

### SLO босгын үндэслэл

- Cart API нь энгийн үйлдэл тул 50 ms-аас бага хариулах хугацаа сонгосон.
- Pay API-д зориудаар 5%-ийн алдаа үүсгэдэг тул 8%-ийн алдааны босго сонгосон.
- Availability-ийн зорилгыг 90%-аас их байхаар тогтоосон.
- Report API 200–400 ms хүлээдэг тул p95-ийн босгыг 450 ms гэж сонгосон.

## 6. k6 Threshold

`slo-test.js` файлд дараах threshold-уудыг тохируулсан.

- `http_req_duration{name:cart}` – p95 < 50 ms
- `http_req_failed{name:pay}` – rate < 0.08
- `checks` – rate > 0.90
- `http_req_duration{name:report}` – p95 < 450 ms

## 8. Chaos тест ба Availability

Chaos тестийг 20 виртуал хэрэглэгчтэй, 2 минут ажиллуулж, серверийг 10 секунд зориудаар зогсоож дахин асаасан.

| Үзүүлэлт | Бодит үр дүн |
|---|---:|
| Нийт HTTP хүсэлт | 5706 |
| Нийт iteration | 1902 |
| Нийт checks | 5706 |
| Checks succeeded | 4938 (86.54%) |
| Checks failed | 768 (13.45%) |
| Cart амжилттай | 1672 |
| Cart амжилтгүй | 230 |
| Report амжилтгүй | 235 |
| Pay амжилтгүй | 303 |

### Request-based Availability

Cart хүсэлтийн амжилтын хувиар хүртээмжийг тооцсон.

Availability = (Амжилттай хүсэлт / Нийт хүсэлт) × 100

= 1672 / 1902 × 100

= **87.91%**

Энэ нь 90%-ийн SLO босгыг хангаагүй.

### Time-based Availability

2 минутын хугацаанд сервер 10 секунд зогссон гэж үзвэл:

Availability = (120 - 10) / 120 × 100

= **91.67%**

Time-based болон request-based availability нь өөр хэмжүүр юм. Time-based нь сервер ажилласан хугацааг, request-based нь амжилттай боловсруулсан хүсэлтийн хувийг хэмждэг.

### Error Budget

90%-ийн SLO-ийн дагуу 120 секундийн хугацаанд зөвшөөрөгдөх тасалдлын хугацаа:

120 × (1 - 0.90) = **12 секунд**

10 секундийн тасалдал нь time-based error budget-ийн хүрээнд байна.

Reliability нь хүсэлт алдаагүй боловсруулах чадварыг, Availability нь систем хэрэгцээтэй үед ажиллаж байх чадварыг илэрхийлнэ. Эдгээр нь холбоотой боловч ижил ойлголт биш юм.

Үр дүнгийн файл: `results/chaos.txt`

## 10. Дүгнэлт

Энэхүү лабораторийн ажлаар чанарын сценарио, SLI, SLO болон k6 threshold-ийн уялдааг судаллаа. Эхлээд Performance, Reliability, Availability гэсэн гурван чанарын сценариог тодорхойлсон. Сценарио бүрийн хувьд системийн төлөв, орчны төлөв, гадаад өдөөлт, шаардлагатай хариу болон хэмжүүрийг тодорхойлсон. Дараа нь эдгээр шаардлагыг хэмжигдэхүйц SLO болгон хувиргасан. k6 ашиглан 20 виртуал хэрэглэгчтэй үндсэн тест ажиллуулж, бүх тохируулсан threshold биелснийг баталгаажуулсан. Chaos тестээр серверийг 10 секунд зогсооход request-based availability 87.91% болж, 90%-ийн зорилтыг хангаагүй. Time-based availability 91.67% гарсан нь хоёр хэмжүүрийн ялгааг харуулсан. Мөн Report API-ийн босгыг зориудаар зөрчиж, k6 FAIL төлөв болон 99 exit code буцаасныг шалгасан. Энэ лаборатори нь чанарын шаардлагыг хэмжиж, автомат тестээр баталгаажуулахын ач холбогдлыг ойлгуулсан.

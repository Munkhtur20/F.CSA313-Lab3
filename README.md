# 4. SLO тодорхойлолт

SLO (Service Level Objective) нь системийн чанарын хэмжүүрт тавьсан зорилтот түвшин юм.

SLI (Service Level Indicator) нь тухайн чанарыг хэмжих үзүүлэлт юм.

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency p95 | < 50 мс | 20 VU, 1 минут |
| Reliability | /pay error rate | < 8% | 20 VU, 1 минут |
| Availability | Амжилттай checks rate | > 90% | 20 VU, 2 минут, 10 секунд crash |
| Нэмэлт Report | /report latency p95 | < 450 мс | 20 VU, 1 минут |

## 4.1 Босго сонгосон үндэслэл

- Performance: localhost дээрх хурдан endpoint-д 50 мс-ийн босго сонгосон. Энэ нь бодит хариу хугацааг хэмжих боломж олгоно.
- Reliability: /pay endpoint зориудаар 5%-ийн алдаа үүсгэдэг тул 8%-ийн босго сонгосон.
- Availability: 90%-ийн босго нь богино хугацааны зогсолтын нөлөөг хэмжих боломж олгоно.
- Report: /report endpoint 200–400 мс хүлээдэг тул 450 мс-ийн p95 босго сонгосон.

## 4.2 Availability Error Budget

Нийт тестийн хугацаа:

2 минут = 120 секунд

SLO = 90%

Error budget:

120 × (1 - 0.90) = 12 секунд

Иймээс 2 минутын хугацаанд 12 секунд хүртэлх зогсолтыг хугацаагаар тооцсон error budget гэж үзнэ.

Chaos туршилтаар серверийг 10 секунд зогсоосон тул хугацааны budget-ээс 2 секунд бага байна.

Гэхдээ k6-ийн checks нь хугацаагаар биш хүсэлтийн тоогоор амжилтын хувийг тооцдог. Сервер унасан үед хүсэлтүүд connection refused болж хурдан буцдаг тул хүсэлтээр тооцсон error budget нь хугацаагаар тооцсоноос ялгаатай гарч болно.

# 6. Chaos Engineering туршилт

Availability сценариог бодитоор шалгахын тулд серверт зориудаар эвдрэл үүсгэсэн.

Туршилтын дараалал:

1. k6 тестийг 2 минут ажиллуулсан.
2. Тест ажиллаж байх үед серверийг Ctrl+C ашиглан зогсоосон.
3. Серверийг 10 секунд зогсолттой байлгасан.
4. Серверийг дахин node server.js командаар ажиллуулсан.
5. k6-ийн үр дүнгээс амжилттай болон амжилтгүй хүсэлтийн тоог шалгасан.

## 6.1 Chaos туршилтын үр дүн

Энд results/chaos.txt файлаас бодит үр дүнгээ оруулна.

- Нийт хүсэлтийн тоо: 
- Амжилттай хүсэлтийн тоо:
- Амжилтгүй хүсэлтийн тоо:
- Availability:
- Availability threshold: PASS / FAIL
- Reliability threshold: PASS / FAIL

Бодит availability тооцох томьёо:

Availability = (Амжилттай хүсэлт / Нийт хүсэлт) × 100%

## 6.2 Availability ба Reliability ялгаа

Availability нь систем хүсэлтэд ерөнхийдөө амжилттай хариулж байгаа эсэхийг хэмждэг. Reliability нь тухайн үйлчилгээ, энэ тохиолдолд төлбөр боловсруулах үйл ажиллагааны алдааны давтамжийг хэмждэг.

Сервер бүрэн зогссон үед хоёр хэмжүүр зэрэг муудаж болох боловч хэвийн үед төлбөрийн алдааг тусад нь хэмжихийн тулд зөвхөн /pay endpoint-ийн хүсэлтүүдийг ашиглах шаардлагатай.

# 7. Threshold-ийг зориудаар FAIL болгох

Нэмэлт туршилтаар /report endpoint-ийн p95 босгыг 100 мс болгож зориудаар өөрчилсөн.

Серверийн /report endpoint нь 200–400 мс хүлээлттэй тул 100 мс-ийн босгыг хангах боломжгүй.

Иймээс дараах үр дүнг шалгасан:

- /report p95 threshold: FAIL
- k6 exit code: results/fail.txt болон Terminal-ийн гаралтаас тэмдэглэнэ.

k6 threshold FAIL болсон үед процесс тэгээс өөр exit code буцаадаг. Энэ нь CI pipeline-д тест амжилтгүй болсныг мэдээлэхэд ашиглагдана.

FAIL хувилбарын кодыг slo-test-fail.js файлд хадгалсан.

# 9. Дүгнэлт

Энэхүү лабораторийн ажлаар чанарын сценарио, SLO болон k6 threshold-ийн уялдааг судаллаа. Эхлээд системийн Performance, Reliability, Availability гэсэн гурван чанарын сценариог тодорхойлсон. Сценарио бүрийн хувьд системийн төлөв, орчны төлөв болон гадаад өдөөлтийг тодорхой бичсэн. Дараа нь эдгээр сценариогоос хэмжиж болох SLI болон SLO босгуудыг гаргасан. k6 ашиглан тодорхойлсон SLO-уудыг автомат threshold болгон хэрэгжүүлсэн. Chaos туршилтаар серверийг зориудаар зогсоож, дахин асаах үеийн системийн ажиллагааг шалгасан. Мөн threshold-ийг зориудаар зөрчиж, k6-ийн FAIL үр дүн болон exit code-ийн ажиллагааг судалсан. Энэ ажлын хамгийн чухал ойлголт нь чанарын шаардлагыг хэмжигдэхүйц үзүүлэлт болгон хувиргаж, автомат тестээр баталгаажуулах явдал байлаа.
